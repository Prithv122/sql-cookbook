# Interview Prep — sql-cookbook

**Five questions, five answers.** An unanswered question means this project is not shipped.

---

### Q1. Walk me through the architecture in 90 seconds.

_A:_ Three directories and a thin Python layer around them.

`recipes/` holds twelve `.sql` files, one analytical pattern each — running totals,
`LAG`/`LEAD`, the three ranking functions, top-N per group, two recursive CTEs,
gaps-and-islands, subscription lapse detection, sessionization, DuckDB `PIVOT`, portable
conditional aggregation, and tie-safe ranking. Each carries a `-- Question:` /
`-- Pattern:` header and runs unmodified in a plain DuckDB shell.

They run against a synthetic warehouse — seven tables, 25k rows — generated by
`warehouse.py` from a fixed seed. Determinism is the foundation everything else stands
on: because the same seed produces the same rows, expected results can be frozen.

`tests/fixtures/` holds those frozen results as JSON, including column names and types.
`test_recipes.py` discovers `recipes/*.sql` by glob, so a recipe added without a fixture
fails the suite rather than shipping untested. `test_semantics.py` goes further and
re-implements the load-bearing recipes in plain Python from the base tables, because a
fixture generated from a query cannot prove that query was ever correct.

`benchmarks/` holds naive and window-function spellings of three of those questions as
separate executable files. `sql-cookbook bench` times them and saves `EXPLAIN ANALYZE`
plans; a test asserts the two spellings return identical rows, because a timing
comparison between queries that answer different questions is meaningless.

### Q2. Why did you choose separate benchmark files over just commenting the naive query inside each recipe?

_A:_ Three reasons, and the third is the one that matters.

Recipes stay copy-pasteable — a reader can select the whole file and paste it into a
shell without stripping a wall of commentary.

The naive query stays executable SQL rather than text inside a comment.

And that executability is what lets `test_benchmarks.py` assert the two spellings return
**identical** results — same values, same column names, same column types. That test has
teeth: it caught a real mismatch where `SUM(INTEGER)` returns `HUGEINT` in DuckDB while
`COUNT(*)` returns `BIGINT`, so my two sessionization variants produced the same numbers
in differently-typed columns. Both casts are now explicit. If the naive query had been a
comment, nothing could have run it, and I would have published a performance comparison
between two queries I had never verified agreed.

### Q3. What's the weakest part of this, and what would break first under load?

_A:_ The loader, and I know exactly where because I already hit its first wall.

I load generated rows by rendering SQL literals into one `INSERT` per table. That was a
measured decision — parameter binding costs ~4,300 µs/row on this machine versus 50
µs/row for literals, taking the build from 58 s to 1.4 s — but it does not scale. At
100× the data I would be building a ~40 MB SQL string per table, and allocation becomes
the bottleneck. The replacement is already measured: CSV plus `COPY` loaded the same
rows in 0.07 s. I did not take it because it drags temp-file handling into a library
whose tests run entirely in memory, which is a bad trade at 25k rows.

Second weakest: fixtures freeze entire result sets, which only works because the recipes
sample down to 6–30 rows. At scale I would freeze a digest — row count, column types,
checksum over ordered rows — and keep full fixtures only where reading the diff is the
point.

The honest caveat on the whole project is that the dataset is synthetic, so the
benchmark numbers describe this data on this engine and nothing more. The README says
so in three places.

### Q4. How do you know it works? What did you measure, and against what baseline?

_A:_ Three independent layers, deliberately, because each catches what the others miss.

**Fixtures** catch drift: 107 tests assert each recipe's exact output including column
types. But a fixture is generated from the query it checks, so it freezes bugs just as
faithfully as correct behaviour.

**Independent re-implementation** catches actual wrongness. `test_semantics.py`
recomputes running totals with a Python accumulator, sessionization with an explicit
30-minute loop, and consecutive-day streaks with a hand-written scan, all from the base
tables, then compares to the SQL. That is a genuine baseline: two implementations that
share no logic agreeing on the answer.

**Property tests** catch recipes that quietly stop demonstrating their point — the
failure mode neither of the above sees. That is not hypothetical: recipe 03 exists to
show how `RANK`, `DENSE_RANK` and `ROW_NUMBER` diverge on ties, and my first data slice
had no ties at all. All three columns came back identical, the query ran, the fixture
matched, and the recipe was worthless. A test now fails if the slice stops producing a
tie or if `RANK` and `DENSE_RANK` ever agree throughout.

Measured outcome: 107 tests, 90% statement coverage, 13.6 s. Benchmarks: the window
spellings ran 1.56×, 1.66× and 2.48× faster than the correlated-subquery baselines,
median of 15 runs after a warmup.

### Q5. Your benchmark says the "naive" correlated subquery is only about 1.6× slower than the window function. Isn't the whole point that it should be dramatically worse — and doesn't that undermine the recipe?

_A:_ It undermines the folklore, not the recipe, and I think the real number is more
interesting than the one I expected.

I expected an order of magnitude. I got 1.56×. So I read the plans instead of adjusting
the claim, and every naive plan contains a `DELIM_JOIN` — DuckDB's decorrelation
operator. The optimizer rewrites the correlated subquery into a join rather than
executing it once per row, so it never goes quadratic. What remains is extra relational
work: naive `01-running-total` plans to three `HASH_JOIN`s and three `HASH_GROUP_BY`s;
the optimized one plans to one of each plus a single `WINDOW`. That is a ~1.6× shape,
and the plans are committed to the repo so anyone can verify it.

The narrow, defensible claim is: on this data, on DuckDB 1.5.5, the window spelling ran
1.6–2.5× faster, and the gap is extra operators rather than quadratic scanning. On an
engine that does not decorrelate subqueries — or once one customer has 8,000 orders
instead of 83 — the same SQL degrades much worse. But this repo does not measure those
engines, so it does not claim them.

I would rather ship a modest number I can defend than a dramatic one a reader could
disprove in a single command. And the recipe's case never rested on speed anyway: the
window version is shorter, has one place where the tiebreaker lives instead of two, and
does not silently disagree with itself on ties.

## 30-second pitch

SQL snippet collections rot silently — a query keeps running while returning subtly
wrong rows, because nothing ever asserted what the right rows were. So I built twelve
advanced SQL patterns as a tested cookbook: each is a copy-pasteable `.sql` file against
a seeded synthetic DuckDB warehouse, pinned to a frozen expected result, with the
load-bearing ones re-implemented in Python and compared so the tests prove the queries
are right rather than merely unchanged. 107 tests, 90% coverage. It also ships naive and
optimized spellings of three queries as separate executable files with committed
`EXPLAIN ANALYZE` plans — which is how I found that DuckDB decorrelates the naive
version into a `DELIM_JOIN`, making it 1.6× slower rather than the order of magnitude
the folklore predicts.
